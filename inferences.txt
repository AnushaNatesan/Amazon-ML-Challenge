4. GROUND TRUTH SINGLETON RATE: EXACTLY 5.585%
--------------------------------------------------------------------------------
- Total Source 1 Reference Entities: 2,206,821
- Singletons (0 matches in S2/S3):     123,247 entities (5.585%)
- Non-Singletons (>= 1 match):        2,083,574 entities (94.415%)
- Average Matches per Non-Singleton:  3.67 records

F_0.5 METRIC STRATEGY:
F_0.5 = (1.25 * Precision * Recall) / (0.25 * Precision + Recall)
- Singletons score 1.0 if an empty list [] is predicted.
- Predicting any false match on a singleton drops the entity score to 0.0.
- False merges are penalized 2x more heavily than missed links.
- The decision threshold for matching must be tuned conservatively.

6. TEXT NORMALIZATION & SYNTHETIC NOISE FINDINGS
--------------------------------------------------------------------------------
a. Artificial Latin Accents Injected as Noise:
   - Random accents injected into English words (e.g., "Prívate", "CÓNSULTANTS").
   - Genuine French records contain natural accents ("Santé", "Président", "Hêtres").
   - Unicode NFKD decomposition strips combining diacritics (0x0300 to 0x036F)
     back to base characters while safely preserving Indic/Devanagari scripts.

b. Asymmetric Legal Entity Placement (Prefixes vs. Suffixes):
   - US & India: Legal forms appear almost exclusively at the END (Inc, Corp, Pvt Ltd).
   - France: Legal forms frequently appear at the BEGINNING in S2/S3 ("SCI Ptit Amicale",
     "SAS Moulin Service", "SARL RBJ Union") or in brackets ("[EURL]").
   - The preprocessing module extracts both prefix and suffix legal forms,
     stripping them from the root name while capturing them as auxiliary features.

c. Zero-Padding in Building Numbers:
   - Numbers are artificially padded with leading zeros (e.g., "K-303" vs "K-00303").
   - Regex normalization strips leading zeros, enabling exact alphanumeric matches.

d. Address Permutation & Abbreviation Expansions:
   - Normalizing abbreviations (Rd -> Road, St -> Street, Ave -> Avenue, Bd -> Boulevard,
     R. -> Rue, Opp -> Opposite, H.No -> House Number) turns mismatched surface forms
     into common canonical roots for token-level Jaccard and Levenshtein comparison.

8. PHASE 3 BLOCKING & CANDIDATE GENERATION FINDINGS
--------------------------------------------------------------------------------
a. Hard Country Partitioning:
   - Partitions target records strictly by 'country' before candidate indexing.
   - Reduces pairwise comparison search space by 60%–85% with 0% ground-truth match loss.

b. Multi-Pass Inverted Index Keys:
   - Key A (Core Name Tokens): Exact clean name, first 2 tokens, individual tokens, sorted tokens.
   - Key B (Numeric & Address): Building number + first name token, building number + address token,
     and distinctive address tokens (>= 5 chars).
   - Key C (Postal / PIN): Postal code + first name token, postal code + address token, exact postal code.
   - Key D (Sparse N-gram & Typos): 4-character prefix and character 3-grams.

c. The Transliteration & DBA Breakthrough:
   - In multiple ground truth pairs (e.g. Red Ventures vs. 'रेड वेंचर्स', Balaji Investment vs.
     'బాలాజీ ఇన్వెస్ట్‌మెంట్', Zander Blue vs. 'zblue.com'), the business name in Source 2/3
     is written in Indic scripts or as a web domain, yielding zero name token overlap.
   - However, distinctive address tokens (e.g. 'banipark', 'jeedimetla', 'meadowmont', 'shahagad')
     remain in English and are identical.
   - Adding distinctive address token keys increased recall from 82.5% to 97.7% - 100.0%.

d. Empirical Recall Ceiling Results:
   - Tested against ground truth matches with 20,000+ distractor records.
   - Achieves a Recall Ceiling >= 97% with 100% entity coverage.
   - Caps candidates at top 40 candidates per Source 1 entity, ensuring downstream
     pairwise classification remains computationally fast and lightweight.


9. PHASE 4 PAIRWISE FEATURE ENGINEERING FINDINGS
--------------------------------------------------------------------------------
a. 33-Dimensional Feature Representation:
   - Name Similarity Features (14 metrics):
     RapidFuzz normalized Levenshtein ratio, Jaro-Winkler similarity, Token Sort Ratio,
     Token Set Ratio, Partial Ratio, character 3-gram Jaccard, word token Jaccard &
     containment, first-token anchor similarity, name length ratio, token count diff,
     and raw unstripped name token set ratio.
   - Address Similarity & Missing Address Handling (6 metrics):
     Address Levenshtein & Jaro-Winkler, Token Set Ratio, token Jaccard & containment,
     and address length ratio.
     Missing Address Protection: Explicit 'addr_is_missing' binary indicator safely
     handles the ~3.3% missing address records without corrupting model gradients.
   - Ternary Disagreement Detection (4 metrics):
     Building numbers: +1.0 (exact match), -1.0 (conflict), 0.0 (missing/neutral).
     Postal codes: +1.0 (exact match), -1.0 (conflict), 0.0 (missing/neutral).
     Postal code 3-digit prefix match and shared numeric token count.
     INFERENCE: Two candidate businesses sharing a city or brand name but with conflicting
     house numbers (e.g., No. 12 vs No. 450) or conflicting postal codes are almost
     always false positives. Ternary -1.0 penalization provides an immense negative signal.
   - Legal Entity Form Compatibility (2 metrics):
     +1.0 (matching legal form e.g. inc vs inc, pvt_ltd vs pvt_ltd),
     -1.0 (conflicting forms e.g. pvt_ltd vs llp, or corp vs ngo),
     0.0 (neutral / unextracted).
   - Candidate Metadata & Composite Anchors (7 metrics):
     Candidate rank position, source indicators (is_source_2, is_source_3),
     name-address interaction overlap, and high-confidence composite anchors
     (exact name match + exact building number match).

10. PHASE 5 SCORING MODEL, THRESHOLD TUNING & SUBMISSION INFERENCES
--------------------------------------------------------------------------------
a. Candidate Class Imbalance:
   - On candidate pairs generated from multi-pass blocking, positive matches represent
     ~0.06% of all candidate pairs (an extreme class imbalance ratio of ~1,615 : 1).
   - Training a standard unweighted classifier results in the majority distractor class
     dominating predictions. Calibrating LightGBM's `scale_pos_weight` (between 10.0 and 25.0)
     upweights the rare true matches, allowing the gradient booster to learn subtle
     similarity boundaries.

b. Most Predictive Feature Hierarchy:
   Empirical feature importance from trained LightGBM:
   1. `name_levenshtein`: Dominant primary signal for core entity alignment.
   2. `name_jaro_winkler`: Captures prefix matching and minor suffix variations.
   3. `name_exact_match`: Immediate high-confidence anchor.
   4. `addr_length_ratio` & `addr_levenshtein`: Address compatibility verification.
   5. `name_token_sort_ratio`: Robust against token permutation and word-order shuffling.

c. Precision-Heavy Macro F_0.5 Decision Threshold Optimization:
   - Because Macro F_0.5 weights precision twice as heavily as recall (beta=0.5), false merges
     penalize the score twice as severely as false dismissals.
   - Grid search across decision thresholds (0.40 - 0.90) demonstrates robust performance
     reaching 99.20% validation Macro F_0.5.
   - Calibrating threshold between 0.40 and 0.75 ensures the pipeline yields high precision
     without missing legitimate matches.
